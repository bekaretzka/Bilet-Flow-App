# Создание обращения BiletFlow — предложение API

Статус: **предложено, ещё не согласовано с backend-командой**. На момент проверки в checkout есть только перечень ожидаемых контрактов в `backend-api-gaps.md`; отдельного контракта поддержки, OpenAPI, backend или веб-клиента нет. В ранее предоставленных `BiletFlow API Reference.md` и `auth-and-roles.md` endpoint поддержки также отсутствует. Ниже описан контракт для текущей мобильной реализации и MockEngine, а не подтверждённый работающий backend.

## Запрос

`POST /support/requests`, `Authorization: Bearer <access_token>`, `Content-Type: application/json`. Любой вошедший пользователь, включая организатора как покупателя; гостю требуется login. Общий refresh допускает один повтор только после явного 401. Пароль, токены и тексты сообщений не журналируются.

```json
{
  "event_id": 101,
  "order_id": 7102,
  "ticket_id": 71020,
  "category": "ticket_issue",
  "subject": "Вопрос о билете",
  "message": "Подскажите, где находится вход для участников?",
  "client_request_id": "68e78a71-d44e-4cff-a34a-296a7007ff32"
}
```

| Поле | Правило |
| --- | --- |
| `event_id` | Обязательный положительный int, контекст мероприятия |
| `order_id`, `ticket_id` | Необязательные положительные int или null; пропущенное поле эквивалентно null |
| `category` | Обязательно: `event_question`, `ticket_issue`, `payment_issue`, `other` |
| `subject` | Обязательная строка, 3–200 Unicode-символов после trim |
| `message` | Обязательная строка, 1–5000 Unicode-символов после trim; переносы внутри сохраняются |
| `client_request_id` | Обязательная строка UUID v4, генерируется клиентом на одну логическую отправку |

Мобильная форма нормализует subject/message через trim перед отправкой; сервер повторяет валидацию. Контекст передаётся автоматически, не вводится посетителем. Все строки — обычный текст, не HTML. Вложения, список обращений, последующие сообщения и ответы организатора в этот контракт не входят.

## Права и контекст

- Без привязки заказа/билета разрешено обращение по опубликованному public/unlisted-событию, доступному через посетительскую страницу. Отсутствующее, private или неопубликованное событие — `404 EventNotFoundError`.
- При привязке `order_id` сервер проверяет `order.user_id == current_user.id` и `order.event_id == event_id`. Организатор мероприятия не получает права привязать заказ другого покупателя. Ошибка — `404 OrderNotFoundError` без раскрытия чужих данных.
- Для `ticket_id` проверяются владелец его заказа, событие и, если передан order_id, принадлежность этому же заказу. Ошибка — `404 TicketNotFoundError`.
- При передаче только ticket_id сервер определяет order_id из билета и возвращает его в контексте ответа. По ticketId нельзя вычислять orderId на клиенте.
- Свой заказ/билет разрешено привязать независимо от статуса заказа или мероприятия, включая cancelled/refunded/expired: именно такие случаи могут требовать помощи. Мероприятие должно существовать. Получатель определяется сервером через organizer profile события, а не переданным пользователем recipient ID.

## Успех и идемпотентность

Первая успешная отправка — `201`. Ответ — отдельная модель `SupportRequest`, не `Order`:

```json
{
  "id": 9000,
  "status": "open",
  "event_id": 101,
  "order_id": 7102,
  "ticket_id": 71020,
  "category": "ticket_issue",
  "subject": "Вопрос о билете",
  "message": "Подскажите, где находится вход для участников?",
  "client_request_id": "68e78a71-d44e-4cff-a34a-296a7007ff32",
  "created_at": "2026-11-24T14:00:00+05:00"
}
```

ID и статус назначает сервер; начальный статус этого шага — `open`. Даты ISO 8601 с UTC-смещением или Z. Nullable order_id/ticket_id в ответе присутствуют явно. Поля category/subject/message/request ID возвращаются для сверки ответа, контекст не должен произвольно меняться.

Уникальность: `(current_user.id, client_request_id)`. Атомарно сохраняются обращение, первое сообщение и результат идемпотентной операции. Повтор с тем же ключом и тем же каноническим телом возвращает **тот же 201, ID, created_at и сохранённый результат**, не создавая второго обращения/сообщения. JSON-порядок ключей не имеет значения; optional missing/null эквивалентны, subject/message сравниваются после trim. Проверка повторного ключа выполняется после аутентификации; сохранённый результат недоступен другому пользователю. Смена статуса события после первого успешного создания не ломает повтор того же запроса. Повтор ключа с другим контекстом, категорией, темой или сообщением — `409 ClientRequestConflictError`.

Идемпотентный результат хранится на срок жизни обращения; TTL, удаление и лимиты хранения должны быть отдельно согласованы. Конкурентные запросы одного ключа сериализуются/защищаются уникальным ограничением БД. Нельзя реализовать это как неатомарную проверку «сначала найти, потом вставить».

Клиент при таймауте или потере ответа сохраняет **неизменяемый снимок тела и ID в памяти формы**. POST автоматически не повторяется после транспортного сбоя. Ручной повтор без изменения данных отправляет тот же снимок. Изменение нормализованного текста/категории означает новую отправку и новый UUID; интерфейс предупреждает, что предыдущая могла уже создать обращение. После успеха повторная отправка заблокирована. После закрытия формы или завершения процесса снимок не восстанавливается; новый процесс не должен заявлять, что предыдущая операция не состоялась. После смены аккаунта форма и снимок очищаются. Ротация токенов внутри той же сессии сохраняет снимок.

## Ошибки

| HTTP | Ошибка | Значение |
| --- | --- | --- |
| 401 | `detail` | Нет/истёк access token; существующая логика refresh |
| 404 | `EventNotFoundError` | Нет доступного события |
| 404 | `OrderNotFoundError` | Нет своего заказа в указанном событии |
| 404 | `TicketNotFoundError` | Нет своего билета в указанном контексте |
| 409 | `ClientRequestConflictError` | ID уже использован с другим телом |
| 422 | `VALIDATION_ERROR` | Ошибки полей, UUID или категории |
| 5xx | `error/message` или `detail` | Сбой сервера, данные формы сохраняются |

```json
{
  "error": "ClientRequestConflictError",
  "message": "client_request_id was already used with another request body",
  "fields": {"client_request_id": "Conflict"}
}
```

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Validation failed",
  "fields": {"subject": "Must contain 3–200 characters"}
}
```

Клиент поддерживает также существующий `detail`-формат ошибок. Неуспех не заменяется моками в release; отсутствующий маршрут показывает фактическую HTTP-ошибку.

## MockEngine и приёмка

Мок хранит обращения по пользователю и request ID, проверяет существующее хранилище заказов/билетов и их принадлежность. Тема `support-unknown` симулирует потерю первого ответа после сохранения, повтор возвращает сохранённое обращение. Тема `support-offline` симулирует недоступную сеть до обработки. Эти переключатели существуют только в debug-моке, не являются полями или правилами настоящего API. Как и другие mock-данные, обращения живут до завершения процесса.

Проверки: создание с события, заказа и билета; отсутствие доступа к чужому заказу/билету; неверный event_id; ошибки полей; двойное нажатие и конкурентный повтор; одинаковый ID/тело даёт один результат; другой текст с прежним ID даёт 409; потерянный ответ → ручной повтор с одним созданным обращением; refresh не меняет ID; login возвращает гостя к форме; смена аккаунта очищает форму и игнорирует поздние ответы. Реальные backend и UI-проверки следует отличать от тестов MockEngine. Список обращений и переписка остаются следующими шагами.

## Чтение обращений и переписки — дополнение шага 47

**Новые предложенные маршруты, ещё не согласованы.** Повторная проверка checkout не обнаружила согласованного API поддержки, OpenAPI, backend или веб-клиента. Это расширение предыдущей модели SupportRequest, а не описание работающего сервера.

Все GET требуют Bearer и доступны только автору обращения. Статус организатора и владение мероприятием не дают права читать чужое обращение через эти посетительские маршруты. Неаутентифицированный запрос — 401 (detail); чужой/отсутствующий ID — одинаковый 404 SupportRequestNotFoundError, без раскрытия данных. Ошибки пагинации — 422 VALIDATION_ERROR; 5xx/сеть не означают пустой список. Общий refresh допускает один повтор после явного 401.

### GET /support/requests/me

Параметры: limit (целое 1–100, default 50), cursor (непрозрачная строка следующей страницы, пропускается для первой). Формат пагинации совпадает с предложенными заказами организатора: {items: [...], next_cursor: string|null}. Сортировка updated_at DESC, id DESC; cursor привязан к пользователю и сортировке. Для обновляющейся истории клиент начинает новый проход после refresh; снимок БД между страницами не гарантируется, клиент исключает дубли по id.

SupportRequest дополняется updated_at (обязательная ISO 8601 дата со смещением) и event_title (nullable строка, если название доступно). Остальные поля прежние; message здесь означает первое сообщение и не является отдельной строкой переписки в UI. Статусы при чтении: open, pending, resolved, closed; неизвестные значения клиент показывает буквально. В этом шаге создание возвращает open, API изменения статуса не предлагается.

```json
{"items":[{"id":9000,"status":"open","event_id":101,"event_title":"Концерт","order_id":null,"ticket_id":null,"category":"event_question","subject":"Вопрос о входе","message":"Где вход?","client_request_id":"68e78a71-d44e-4cff-a34a-296a7007ff32","created_at":"2026-11-24T14:00:00+05:00","updated_at":"2026-11-24T14:00:00+05:00"}],"next_cursor":null}
```

### GET /support/requests/{request_id}

Положительный серверный ID. 200 — актуальный SupportRequest, той же структуры, что элемент списка, без обёртки. Авторство проверяется до выдачи контекста. Изменение доступности мероприятия не лишает автора доступа к уже созданному обращению.

### GET /support/requests/{request_id}/messages

Параметры limit/cursor и обёртка items/next_cursor те же. Сообщения идут created_at DESC, id DESC: первая страница содержит самые новые, cursor ведёт к более старым. Внутри обращения серверные ID монотонно возрастают по времени; одинаковые даты упорядочены по ID. Курсор привязан к автору, обращению и границе страницы; клиент не конструирует его. Мобильный экран показывает старые сообщения выше новых, исключает дубли по серверному id и сохраняет видимую строку при подгрузке старых через stable keys/reverseLayout.

```json
{"items":[{"id":9000,"request_id":9000,"author_name":null,"author_role":"visitor","text":"Где вход?","created_at":"2026-11-24T14:00:00+05:00"}],"next_cursor":null}
```

Поля сообщения: положительные id и request_id; author_name nullable отображаемое имя; author_role visitor/organizer/system; text непустая строка обычного текста; created_at ISO 8601 со смещением. Для неизвестной роли UI использует нейтральную подпись. Отправка новых сообщений, ответы организатора и смена статусов остаются вне этого шага.

Первое сообщение сохраняется атомарно при POST создания и возвращается этим GET **ровно один раз**. Идемпотентный повтор создания не добавляет сообщений. Мок проецирует одно первое сообщение из единственной сохранённой записи; ID сообщения независим по смыслу от ID обращения (совпадение чисел в mock не является правилом API). Новые mock-обращения появляются в списке текущего пользователя. Переписка с несколькими страницами и пересекающимися результатами дополнительно проверяется тестовым HTTP-транспортом; фиктивные ответы организатора к настоящим обращениям не добавляются.

Критерии приёмки: гость получает приглашение войти с возвратом в раздел; новый POST появляется в списке; первое сообщение одно после повтора; страницы списка/сообщений без дублей; старые сообщения не сдвигают видимую строку; refresh/retry сохраняют прочитанное при ошибке; чужой аккаунт получает 404; смена аккаунта очищает данные и исключает поздние ответы; возврат ведёт в список либо результат создания. Настоящий сервер и ручной UI следует проверять отдельно от MockEngine.
