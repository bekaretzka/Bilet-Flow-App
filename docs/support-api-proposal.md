# Создание обращения BiletFlow — предложение API

Статус: **предложено, ещё не согласовано с backend-командой**. На момент проверки в checkout есть только перечень ожидаемых контрактов в `backend-api-gaps.md`; отдельного контракта поддержки, OpenAPI, backend или веб-клиента нет. В ранее предоставленных `BiletFlow API Reference.md` и `auth-and-roles.md` endpoint поддержки также отсутствует. Ниже описан контракт для текущей мобильной реализации и MockEngine, а не подтверждённый работающий backend.

## Запрос

`POST /support/requests`, `Authorization: Bearer <access_token>`, `Content-Type: application/json`. Любой вошедший пользователь, включая организатора как покупателя; гостю требуется login. Общий refresh допускает один повтор только после явного 401. Пароль, токены и тексты сообщений не журналируются.

```json
{
  "event_id": 101,
  "order_id": 7102,
  "ticket_id": 71020,
  "category": "ticket_issue",
  "subject": "Вопрос о билете",
  "message": "Подскажите, где находится вход для участников?",
  "client_request_id": "68e78a71-d44e-4cff-a34a-296a7007ff32"
}
```

| Поле | Правило |
| --- | --- |
| `event_id` | Обязательный положительный int, контекст мероприятия |
| `order_id`, `ticket_id` | Необязательные положительные int или null; пропущенное поле эквивалентно null |
| `category` | Обязательно: `event_question`, `ticket_issue`, `payment_issue`, `other` |
| `subject` | Обязательная строка, 3–200 Unicode-символов после trim |
| `message` | Обязательная строка, 1–5000 Unicode-символов после trim; переносы внутри сохраняются |
| `client_request_id` | Обязательная строка UUID v4, генерируется клиентом на одну логическую отправку |

Мобильная форма нормализует subject/message через trim перед отправкой; сервер повторяет валидацию. Контекст передаётся автоматически, не вводится посетителем. Все строки — обычный текст, не HTML. Вложения, список обращений, последующие сообщения и ответы организатора в этот контракт не входят.

## Права и контекст

- Без привязки заказа/билета разрешено обращение по опубликованному public/unlisted-событию, доступному через посетительскую страницу. Отсутствующее, private или неопубликованное событие — `404 EventNotFoundError`.
- При привязке `order_id` сервер проверяет `order.user_id == current_user.id` и `order.event_id == event_id`. Организатор мероприятия не получает права привязать заказ другого покупателя. Ошибка — `404 OrderNotFoundError` без раскрытия чужих данных.
- Для `ticket_id` проверяются владелец его заказа, событие и, если передан order_id, принадлежность этому же заказу. Ошибка — `404 TicketNotFoundError`.
- При передаче только ticket_id сервер определяет order_id из билета и возвращает его в контексте ответа. По ticketId нельзя вычислять orderId на клиенте.
- Свой заказ/билет разрешено привязать независимо от статуса заказа или мероприятия, включая cancelled/refunded/expired: именно такие случаи могут требовать помощи. Мероприятие должно существовать. Получатель определяется сервером через organizer profile события, а не переданным пользователем recipient ID.

## Успех и идемпотентность

Первая успешная отправка — `201`. Ответ — отдельная модель `SupportRequest`, не `Order`:

```json
{
  "id": 9000,
  "status": "open",
  "event_id": 101,
  "order_id": 7102,
  "ticket_id": 71020,
  "category": "ticket_issue",
  "subject": "Вопрос о билете",
  "message": "Подскажите, где находится вход для участников?",
  "client_request_id": "68e78a71-d44e-4cff-a34a-296a7007ff32",
  "created_at": "2026-11-24T14:00:00+05:00"
}
```

ID и статус назначает сервер; начальный статус этого шага — `open`. Даты ISO 8601 с UTC-смещением или Z. Nullable order_id/ticket_id в ответе присутствуют явно. Поля category/subject/message/request ID возвращаются для сверки ответа, контекст не должен произвольно меняться.

Уникальность: `(current_user.id, client_request_id)`. Атомарно сохраняются обращение, первое сообщение и результат идемпотентной операции. Повтор с тем же ключом и тем же каноническим телом возвращает **тот же 201, ID, created_at и сохранённый результат**, не создавая второго обращения/сообщения. JSON-порядок ключей не имеет значения; optional missing/null эквивалентны, subject/message сравниваются после trim. Проверка повторного ключа выполняется после аутентификации; сохранённый результат недоступен другому пользователю. Смена статуса события после первого успешного создания не ломает повтор того же запроса. Повтор ключа с другим контекстом, категорией, темой или сообщением — `409 ClientRequestConflictError`.

Идемпотентный результат хранится на срок жизни обращения; TTL, удаление и лимиты хранения должны быть отдельно согласованы. Конкурентные запросы одного ключа сериализуются/защищаются уникальным ограничением БД. Нельзя реализовать это как неатомарную проверку «сначала найти, потом вставить».

Клиент при таймауте или потере ответа сохраняет **неизменяемый снимок тела и ID в памяти формы**. POST автоматически не повторяется после транспортного сбоя. Ручной повтор без изменения данных отправляет тот же снимок. Изменение нормализованного текста/категории означает новую отправку и новый UUID; интерфейс предупреждает, что предыдущая могла уже создать обращение. После успеха повторная отправка заблокирована. После закрытия формы или завершения процесса снимок не восстанавливается; новый процесс не должен заявлять, что предыдущая операция не состоялась. После смены аккаунта форма и снимок очищаются. Ротация токенов внутри той же сессии сохраняет снимок.

## Ошибки

| HTTP | Ошибка | Значение |
| --- | --- | --- |
| 401 | `detail` | Нет/истёк access token; существующая логика refresh |
| 404 | `EventNotFoundError` | Нет доступного события |
| 404 | `OrderNotFoundError` | Нет своего заказа в указанном событии |
| 404 | `TicketNotFoundError` | Нет своего билета в указанном контексте |
| 409 | `ClientRequestConflictError` | ID уже использован с другим телом |
| 422 | `VALIDATION_ERROR` | Ошибки полей, UUID или категории |
| 5xx | `error/message` или `detail` | Сбой сервера, данные формы сохраняются |

```json
{
  "error": "ClientRequestConflictError",
  "message": "client_request_id was already used with another request body",
  "fields": {"client_request_id": "Conflict"}
}
```

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Validation failed",
  "fields": {"subject": "Must contain 3–200 characters"}
}
```

Клиент поддерживает также существующий `detail`-формат ошибок. Неуспех не заменяется моками в release; отсутствующий маршрут показывает фактическую HTTP-ошибку.

## MockEngine и приёмка

Мок хранит обращения по пользователю и request ID, проверяет существующее хранилище заказов/билетов и их принадлежность. Тема `support-unknown` симулирует потерю первого ответа после сохранения, повтор возвращает сохранённое обращение. Тема `support-offline` симулирует недоступную сеть до обработки. Эти переключатели существуют только в debug-моке, не являются полями или правилами настоящего API. Как и другие mock-данные, обращения живут до завершения процесса.

Проверки: создание с события, заказа и билета; отсутствие доступа к чужому заказу/билету; неверный event_id; ошибки полей; двойное нажатие и конкурентный повтор; одинаковый ID/тело даёт один результат; другой текст с прежним ID даёт 409; потерянный ответ → ручной повтор с одним созданным обращением; refresh не меняет ID; login возвращает гостя к форме; смена аккаунта очищает форму и игнорирует поздние ответы. Реальные backend и UI-проверки следует отличать от тестов MockEngine. Список обращений и переписка остаются следующими шагами.

## Чтение обращений и переписки — дополнение шага 47

**Новые предложенные маршруты, ещё не согласованы.** Повторная проверка checkout не обнаружила согласованного API поддержки, OpenAPI, backend или веб-клиента. Это расширение предыдущей модели SupportRequest, а не описание работающего сервера.

Все GET требуют Bearer и доступны только автору обращения. Статус организатора и владение мероприятием не дают права читать чужое обращение через эти посетительские маршруты. Неаутентифицированный запрос — 401 (detail); чужой/отсутствующий ID — одинаковый 404 SupportRequestNotFoundError, без раскрытия данных. Ошибки пагинации — 422 VALIDATION_ERROR; 5xx/сеть не означают пустой список. Общий refresh допускает один повтор после явного 401.

### GET /support/requests/me

Параметры: limit (целое 1–100, default 50), cursor (непрозрачная строка следующей страницы, пропускается для первой). Формат пагинации совпадает с предложенными заказами организатора: {items: [...], next_cursor: string|null}. Сортировка updated_at DESC, id DESC; cursor привязан к пользователю и сортировке. Для обновляющейся истории клиент начинает новый проход после refresh; снимок БД между страницами не гарантируется, клиент исключает дубли по id.

SupportRequest дополняется updated_at (обязательная ISO 8601 дата со смещением) и event_title (nullable строка, если название доступно). Остальные поля прежние; message здесь означает первое сообщение и не является отдельной строкой переписки в UI. Статусы при чтении: open, pending, resolved, closed; неизвестные значения клиент показывает буквально. В этом шаге создание возвращает open, API изменения статуса не предлагается.

```json
{"items":[{"id":9000,"status":"open","event_id":101,"event_title":"Концерт","order_id":null,"ticket_id":null,"category":"event_question","subject":"Вопрос о входе","message":"Где вход?","client_request_id":"68e78a71-d44e-4cff-a34a-296a7007ff32","created_at":"2026-11-24T14:00:00+05:00","updated_at":"2026-11-24T14:00:00+05:00"}],"next_cursor":null}
```

### GET /support/requests/{request_id}

Положительный серверный ID. 200 — актуальный SupportRequest, той же структуры, что элемент списка, без обёртки. Авторство проверяется до выдачи контекста. Изменение доступности мероприятия не лишает автора доступа к уже созданному обращению.

### GET /support/requests/{request_id}/messages

Параметры limit/cursor и обёртка items/next_cursor те же. Сообщения идут created_at DESC, id DESC: первая страница содержит самые новые, cursor ведёт к более старым. Внутри обращения серверные ID монотонно возрастают по времени; одинаковые даты упорядочены по ID. Курсор привязан к автору, обращению и границе страницы; клиент не конструирует его. Мобильный экран показывает старые сообщения выше новых, исключает дубли по серверному id и сохраняет видимую строку при подгрузке старых через stable keys/reverseLayout.

```json
{"items":[{"id":9000,"request_id":9000,"author_name":null,"author_role":"visitor","text":"Где вход?","created_at":"2026-11-24T14:00:00+05:00"}],"next_cursor":null}
```

Поля сообщения: положительные id и request_id; author_name nullable отображаемое имя; author_role visitor/organizer/system; text непустая строка обычного текста; created_at ISO 8601 со смещением. Для неизвестной роли UI использует нейтральную подпись. Отправка новых сообщений, ответы организатора и смена статусов остаются вне этого шага.

Первое сообщение сохраняется атомарно при POST создания и возвращается этим GET **ровно один раз**. Идемпотентный повтор создания не добавляет сообщений. Мок проецирует одно первое сообщение из единственной сохранённой записи; ID сообщения независим по смыслу от ID обращения (совпадение чисел в mock не является правилом API). Новые mock-обращения появляются в списке текущего пользователя. Переписка с несколькими страницами и пересекающимися результатами дополнительно проверяется тестовым HTTP-транспортом; фиктивные ответы организатора к настоящим обращениям не добавляются.

Критерии приёмки: гость получает приглашение войти с возвратом в раздел; новый POST появляется в списке; первое сообщение одно после повтора; страницы списка/сообщений без дублей; старые сообщения не сдвигают видимую строку; refresh/retry сохраняют прочитанное при ошибке; чужой аккаунт получает 404; смена аккаунта очищает данные и исключает поздние ответы; возврат ведёт в список либо результат создания. Настоящий сервер и ручной UI следует проверять отдельно от MockEngine.

## Сообщения посетителя и обновление — шаг 48

**Предложенный контракт, ещё не согласован.** На повторной проверке проекта согласованного контракта поддержки, OpenAPI или исходников backend не появилось. Этот раздел дополняет шаги 46–47; прежние фразы «отправка вне шага» относятся только к объёму тех шагов.

### POST /support/requests/{request_id}/messages

Bearer, JSON. Только автор обращения; организатор не получает права писать через посетительский endpoint в чужое обращение. Тело:

```json
{"body":"Спасибо! Подскажите время открытия входа.","client_request_id":"68e78a71-d44e-4cff-a34a-296a7007ff32"}
```

body — обязательная строка обычного текста, trim по краям, 1–5000 Unicode code points, внутренние переносы сохраняются. client_request_id — обязательный UUID v4. request_id — положительный серверный ID. Автор, роль и дата назначаются сервером; клиент их не передаёт. 201 возвращает SupportMessage существующего GET (поле текста в ответе называется text):

```json
{"id":100000,"request_id":9000,"author_name":null,"author_role":"visitor","text":"Спасибо! Подскажите время открытия входа.","created_at":"2026-11-25T10:00:00+05:00"}
```

Атомарная идемпотентность по (user_id, request_id, client_request_id): одинаковый нормализованный body возвращает прежние 201/сообщение/время; другой body — 409 ClientRequestConflictError. Срок хранения результата — срок жизни обращения, как при создании. Права проверяются до чтения идемпотентного результата. Сохранённый успешный повтор разрешён и после закрытия; новое сообщение разрешено только в open/pending. resolved и closed — 409 SupportRequestClosedError, без автоматического открытия обращения; неизвестный статус UI считает недоступным для отправки. Закрытие должно проверяться атомарно с созданием сообщения. Первый текст обращения остаётся первым сообщением, повтор POST не дублирует его.

Ошибки: 401 detail (общий refresh и максимум один повтор); 404 SupportRequestNotFoundError для отсутствующего/чужого обращения; 422 VALIDATION_ERROR с fields.body / fields.client_request_id; 409 ClientRequestConflictError или SupportRequestClosedError; 5xx error/message или detail. Клиент сохраняет текст и показывает фактическую HTTP-ошибку; при конфликте закрытия обновляет сведения. После timeout/обрыва или 5xx ручной повтор неизменённого текста использует тот же снимок body/UUID; автоматического транспортного повтора POST нет. Изменение нормализованного текста — новый UUID с предупреждением о возможном сохранении прежнего сообщения. После успеха поле очищается, ответ сливается по серверному ID. Снимок только в памяти до смены обращения/аккаунта/закрытия экрана.

### Получение новых сообщений без пропусков

GET /support/requests/{request_id}/messages дополняется after_id (целое >=0). Без after_id остаётся прежний режим старых страниц DESC. С after_id сервер возвращает только id > after_id **ASC**, limit 1–100 (default 50). next_cursor — непрозрачный курсор следующих новых сообщений, привязанный к обращению/пользователю/after_id. На каждой следующей странице клиент передаёт прежний after_id и полученный cursor; это продолжает ASC-проход, а не начинает DESC-историю. ID внутри обращения строго возрастают в порядке фиксации сообщений; новые сообщения не могут появиться с ID ниже уже выданной границы. Удаление/редактирование сообщений этим контрактом не предусмотрено.

Клиент хранит отдельно high-water последнего завершённого GET-прохода. Первая DESC-страница задаёт начальную границу; затем собираются **все** ASC-страницы после неё до next_cursor=null. Только после полного успеха граница продвигается. Ответ POST добавляет сообщение на экран, но не продвигает high-water: иначе можно пропустить предшествующий ответ другого автора. Ошибка/отмена прохода оставляет границу прежней. Повтор безопасен благодаря дедупликации по ID. Подгрузка старых страниц имеет независимый cursor и не меняет границу новых. Коллизии обновления, отправки и чтения истории объединяются по ID с сохранением времени сервера.

Обновление каждые 10 секунд только пока экран переписки открыт и lifecycle RESUMED; при уходе/фоновой работе GET новых отменяется и таймер останавливается. На экране есть ручное обновление. На последних сообщениях новые показываются с прокруткой к концу; при чтении истории stable keys сохраняют видимое сообщение, появляется действие «Новые сообщения». POST не повторяется автоматически при возвращении из фона. При смене обращения/аккаунта снимок и результаты очищаются, поздние ответы не применяются.

MockEngine хранит первое и последующие сообщения, обновляет updated_at. Текст message-unknown теряет первый ответ после сохранения; повтор с тем же ID возвращает единственное сообщение. message-offline даёт транспортный сбой до сохранения. Создание обращения с темой support-closed возвращает open, а последующее чтение воспроизводит закрытое сервером обращение. Эти переключатели — только debug-сценарии. Release использует настоящий API без fallback. Отправка организатором и управление статусами по-прежнему не реализуются.

## Обращения мероприятия и ответы владельца — предложение шага 49

**Предложено, ещё не согласовано с backend-командой.** В проекте не обнаружен согласованный контракт организаторской поддержки. Этот раздел расширяет права чтения и отправки из шагов 47–48; прежние ограничения «только автор» сохраняются для списка /me, но для отдельных обращений заменяются правилами ниже. Это предложение, а не подтверждение реализации backend или проверки работающего сервера.

### GET /organizer/events/{event_id}/support/requests

Новый защищённый маршрут. Bearer и общий refresh. Доступ имеет только пользователь — владелец organizer profile мероприятия; назначение сотрудником проверки входа, approved-профиль другого организатора и владение чужим заказом такого доступа не дают. Статус мероприятия draft/published/cancelled не ограничивает чтение уже созданных обращений владельцем.

Параметры: limit — целое 1–100, default 50; cursor — непрозрачная строка, пропускается на первой странице. Ответ 200: существующая обёртка {items: SupportRequest[], next_cursor: string|null}. Сортировка updated_at DESC, id DESC. Курсор привязан к текущему пользователю, event_id и сортировке. Обновление начинает новый проход; клиент исключает дубли по серверному ID. Возвращаются только обращения с request.event_id == event_id; клиент дополнительно проверяет контекст каждого элемента.

SupportRequest дополняется полями author_id (положительный ID посетителя), author_name и author_email (nullable строки). Эти поля назначает сервер; клиент их не передаёт при создании и не вычисляет из заказов/билетов. При отсутствии имени и email интерфейс использует подпись «Посетитель». Остальные поля и nullable-контекст остаются прежними.

```json
{"items":[{"id":9000,"event_id":101,"event_title":"Концерт","order_id":null,"ticket_id":null,"author_id":100,"author_name":null,"author_email":"visitor@example.kz","status":"open","category":"event_question","subject":"Вопрос о входе","message":"Где вход?","client_request_id":"68e78a71-d44e-4cff-a34a-296a7007ff32","created_at":"2026-11-24T14:00:00+05:00","updated_at":"2026-11-25T10:00:00+05:00"}],"next_cursor":null}
```

Ошибки списка: 401 detail; 404 EventNotFoundError; 403 EventAccessDeniedError для существующего чужого мероприятия; 422 VALIDATION_ERROR с полями пагинации; сетевой сбой и 5xx не заменяются пустым списком.

### Расширение существующих маршрутов переписки

- GET /support/requests/{request_id}
- GET /support/requests/{request_id}/messages
- POST /support/requests/{request_id}/messages

Автор обращения **или текущий владелец его мероприятия** может читать сведения/сообщения и отправлять ответы. Проверка владельца выполняется по request.event_id и organizer profile на сервере при каждом запросе; переданный клиентом контекст не является доказательством права. Посторонний пользователь, другой организатор и обычный сотрудник получают одинаковый 404 SupportRequestNotFoundError, без раскрытия чужих данных. GET /support/requests/me по-прежнему показывает только обращения, созданные самим пользователем, а не все обращения его мероприятий.

Тело POST прежнее: body 1–5000 Unicode code points после trim, client_request_id UUID v4. Ответ 201 — существующий SupportMessage. Сервер определяет автора: если отправитель является автором обращения, author_role=visitor; иначе при наличии права владельца author_role=organizer. author_name nullable, интерфейс всегда показывает понятную роль и доступное имя. Владелец, создавший собственное обращение как посетитель, не меняет роль только из-за владения мероприятием.

Идемпотентность, closed/resolved, неизвестный результат и запрет автоматического транспортного повтора остаются как в шаге 48. Ключ (sender_user_id, request_id, client_request_id) исключает конфликт идентификаторов разных авторов. До выдачи сохранённого результата повторно проверяются права; отзыв владения не даёт прочитать старый ответ через повтор. Сохранение сообщения, результата идемпотентности и updated_at обращения атомарно. Идемпотентный повтор не меняет updated_at и не добавляет сообщение.

Пагинация старых сообщений, ASC-проход after_id со всеми страницами, отдельная граница завершённого GET и обновление каждые 10 секунд в RESUMED используются без изменений. Отправка ответа не продвигает границу чтения. При смене аккаунта или event_id клиент очищает список, переписку и черновик, останавливает обновление и игнорирует старые ответы. Возврат из переписки ведёт к списку обращений исходного мероприятия; из списка — к управлению этим мероприятием.

Критерии приёмки: посетитель создаёт обращение → владелец видит его в списке и отвечает → посетитель читает ответ с ролью организатора; несколько страниц без дублей; retry/refresh; потерянный ответ с единственным сообщением; отказ постороннему/другому организатору/сотруднику; очистка при смене сессии и события. Ручная визуальная проверка сохранения позиции при подгрузке истории остаётся открытой. Управление статусами не входит в этот шаг.

## Статусы по SRS и изменение владельцем — шаг 50

**Предложенный контракт, ещё не согласован.** Согласованный API или отдельный SRS-файл в checkout не обнаружен. За основу взяты четыре статуса SRS, перечисленные в задании. Этот раздел заменяет прежнюю схему open/pending/resolved/closed и прежние правила отправки в шагах 47–49.

| SRS | Серверное значение | RU |
| --- | --- | --- |
| Open | open | Открыто |
| In Progress | in_progress | В работе |
| Waiting for Customer | waiting_for_customer | Ожидает ответа посетителя |
| Resolved | resolved | Решено |

Совместимость: pending мигрирует в in_progress; closed — в resolved; open/resolved сохраняются. Мок больше не выдаёт pending/closed. Клиент понимает старые значения при чтении, но новая операция отправляет только четыре канонических значения. Неизвестное значение показывается буквально и запрещает изменения/новые сообщения. Не вводится пятый статус Closed. Старый debug-сценарий support-closed теперь возвращает resolved при чтении.

### PATCH /support/requests/{request_id}/status

Bearer, application/json. Только текущий владелец organizer profile мероприятия обращения, включая случай, когда он сам автор обращения. Сотрудник проверки входа, посетитель и другой организатор не могут менять статус. Чтение SupportRequest дополняется can_manage_status: boolean (для текущего аутентифицированного пользователя). Отсутствие поля клиент трактует как false. Это подсказка UI, сервер повторно проверяет право на PATCH.

```json
{"status":"in_progress","expected_status":"open"}
```

Оба поля обязательны и содержат каноническое значение из таблицы. expected_status — последнее успешно прочитанное состояние, для атомарной защиты от чужой смены статуса между чтением и записью.

Переходы: каждый из активных open/in_progress/waiting_for_customer можно перевести в любой другой активный или resolved. Из resolved разрешён только open (явное повторное открытие владельцем). Отправка сообщений не меняет статус автоматически. Новый статус, уже совпадающий с текущим, возвращает 200 без повторного изменения updated_at; это безопасная повторная установка, в том числе после явного 401. Для остальных изменений несовпадение expected_status даёт 409 SupportStatusConflictError. Проверка прав, текущего статуса, перехода и запись атомарны.

200 — полный серверный SupportRequest с актуальными status, updated_at и can_manage_status, того же формата, что GET. Изменение статуса обновляет updated_at, не создаёт сообщение и не меняет client_request_id создания. История действий/уведомления этим шагом не определяются.

Ошибки: 401 detail (общий refresh с максимум одним повтором); 404 SupportRequestNotFoundError; 403 SupportStatusAccessDeniedError; 422 VALIDATION_ERROR с полями status/expected_status; 409 SupportStatusConflictError (состояние изменилось) или SupportStatusTransitionError (переход запрещён); 5xx error/message либо detail. При конфликте клиент перечитывает GET /support/requests/{request_id}. При timeout/обрыве/5xx результат неизвестен: PATCH автоматически не повторяется, повторные изменения и отправка блокируются до успешного GET. UI предлагает «Проверить обращение». Ошибка GET не снимает блокировку; данные другой сессии/обращения не применяются. При сетевом отказе самого refresh до PATCH результат изменения не считается неизвестным.

### Сообщения и обновление

Новые сообщения посетителя и владельца разрешены в open/in_progress/waiting_for_customer. В resolved оба получают 409 SupportRequestClosedError; UI сохраняет введённый текст и показывает объяснение. Чтобы продолжить переписку, владелец явно выполняет resolved → open, после чего отправка снова разрешена. Сохранённый идемпотентный повтор уже созданного сообщения всё ещё возвращает прежний результат даже в resolved, после проверки прав. Он не создаёт нового сообщения и не открывает обращение.

Каждый 10-секундный цикл на активном экране получает также GET сведений обращения: status не выводится из GET messages/after_id. Во время изменения статуса устаревшие GET не могут затереть результат PATCH. После неизвестного результата фоновое чтение статуса приостановлено до явной проверки пользователем; чтение сообщений не снимает блокировку. После успешного PATCH экран и сохранённая строка списка используют серверный ответ; при возврате список обновляется. При смене аккаунта/обращения защищённые сведения и состояние операции очищаются.

MockEngine хранит канонический статус для каждого обращения, проверяет права/переходы и отражает результат в обоих списках и GET деталей. Тема status-unknown теряет ответ первого успешного изменения статуса после записи. Проверка выполняется обычным GET без повторного PATCH. Это debug-сценарий; release не подменяет ошибку реального API моками.

Debug-проверка истории: тема support-history при создании обращения добавляет к первому сообщению 65 явно тестовых строк History 1…65 в MockEngine. Это только тестовая переписка для визуальной проверки двух страниц, не новый маршрут API и не настоящие ответы организатора. GET возвращает обычную пагинацию по 50 сообщений; повтор создания не добавляет строк. Целевой host-тест проверяет 66 уникальных ID и одно первое сообщение.
