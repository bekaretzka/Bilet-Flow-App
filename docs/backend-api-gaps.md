В текущем checkout нет backend, веб-клиента, OpenAPI и более свежих копий указанных контрактов. Работающий сервер в этом шаге не проверялся. MockEngine и клиентский код не считаются доказательством реализации backend. В отношении двух рассматриваемых пробелов документы согласуются; более поздний документ уточняет порядок проверок доступа и ограничения публичного чтения.

Для новых маршрутов предлагается отдельный префикс `/organizer/events/...`, чтобы не менять поведение публичных и покупательских GET. Название префикса также требует согласования. Все запросы защищены `Authorization: Bearer <access_token>`, без тела. Денежные значения — целые тенге, без float; `total_amount` клиент читает как `Long`. Даты — ISO 8601 с UTC-смещением либо `Z`; nullable-поля возвращаются явно как `null`. Ответы и ошибки — JSON. Персональные данные нельзя включать в публичный ответ или журналировать вместе с токенами.

## 1. Заказы мероприятия для организатора

### Существующий контракт и мобильный сценарий

Существуют:

- `GET /events/{event_id}/attendees`: одна строка на билет, включая `order_id`, имя участника и email покупателя. Здесь нет статуса заказа, его `total_amount` и `refunded_at`. Несколько строк могут относиться к одному заказу.
- `GET /orders/me` и `GET /orders/{order_id}`: покупательские чтения. Организатор не может читать чужой заказ через них; по `auth-and-roles.md` получает `404 OrderNotFoundError`.
- `GET /events/{event_id}/sales`: агрегаты продаж; не заменяют данные конкретного заказа.
- `POST /orders/{order_id}/refund`: полный тестовый возврат оплаченного заказа в статусе `confirmed`; тело `{"reason":"..."}`, длина причины 3–500 символов, успех `200` с серверным `Order`.

В приложении реализованы список участников, продажи, `OrdersRepository.refundOrder`, общий refresh и mock-проверки возврата. Организаторский интерфейс возврата ожидает доступного источника статуса и суммы заказа, а также чтения после неизвестного результата. Нельзя выводить допустимость возврата из цены типа, статуса билета, вычислять `order_id` из `ticket_id` или использовать сумму из сводки продаж.

### Новые, ещё не согласованные endpoints

| Предлагаемый запрос | Успех | Назначение |
| --- | --- | --- |
| `GET /organizer/events/{event_id}/orders` | `200 Page<OrganizerOrder>` | Заказы выбранного собственного мероприятия |
| `GET /organizer/events/{event_id}/orders/{order_id}` | `200 OrganizerOrder` | Актуальное состояние одного заказа в контексте события |

Path-параметры — положительные целые ID. Заказы читаются для `draft`, `published`, `cancelled`, при любой visibility; статус события не должен препятствовать проверке уже совершённого возврата.

Query списка:

| Параметр | Предлагаемое правило |
| --- | --- |
| `limit` | По умолчанию 50, от 1 до 100 |
| `cursor` | Необязательный непрозрачный курсор следующей страницы |
| `status` | Необязательный один из `pending`, `confirmed`, `cancelled`, `refunded`, `expired`; отсутствие означает все статусы |

Порядок фиксирован: `created_at DESC, id DESC`. Курсор привязан к событию, фильтру и последнему ключу сортировки; его нельзя переносить между запросами с другим контекстом. Невалидный или несовместимый курсор — `422 VALIDATION_ERROR`. `next_cursor: null` означает конец. Пустая страница — `items: []`, не 404. `total` не требуется. Это keyset-пагинация без обещания общего снимка: при изменении статусов фильтрованный список следует обновить с первой страницы; точное состояние выбранного заказа проверяется отдельным GET.

**Новая проекция `OrganizerOrder`**, а не сокращённый покупательский `Order`:

| Поле | Тип и смысл |
| --- | --- |
| `id`, `event_id` | Обязательные int; серверная принадлежность заказа |
| `status` | Обязательный enum статусов `Order` |
| `total_amount` | Обязательное неотрицательное целое KZT; исходная полная сумма заказа, не уменьшается до нуля после refund |
| `buyer_name`, `buyer_email` | Обязательные string из заказа, без догадок из данных участника |
| `created_at` | Обязательное datetime; сортировка и отображение |
| `paid_at` | Обязательное datetime или null; факт оплаты |
| `refunded_at` | Обязательное datetime или null; время завершённого возврата |

`items`, QR-коды и `tickets` в этой минимальной проекции не нужны. Клиенту потребуется отдельный DTO: нельзя десериализовать проекцию в `Order` и трактовать отсутствующие `tickets` как реальный пустой список. После refund существующий полный `Order` проецируется на те же поля без переименований.

Пример `GET /organizer/events/500/orders?limit=1&status=confirmed`:

```json
{
  "items": [
    {
      "id": 7200,
      "event_id": 500,
      "status": "confirmed",
      "total_amount": 3000,
      "buyer_name": "Анна Иванова",
      "buyer_email": "anna@example.kz",
      "created_at": "2026-11-24T12:00:00+05:00",
      "paid_at": "2026-11-24T12:02:00+05:00",
      "refunded_at": null
    }
  ],
  "next_cursor": "opaque-order-cursor"
}
```

Пример отдельного GET после успешного возврата:

```json
{
  "id": 7200,
  "event_id": 500,
  "status": "refunded",
  "total_amount": 3000,
  "buyer_name": "Анна Иванова",
  "buyer_email": "anna@example.kz",
  "created_at": "2026-11-24T12:00:00+05:00",
  "paid_at": "2026-11-24T12:02:00+05:00",
  "refunded_at": "2026-11-24T13:00:00+05:00"
}
```

### Доступ и ошибки

Предлагается сохранить порядок organizer-проверок из `auth-and-roles.md`:

1. Проверить access token.
2. Получить organizer profile текущего пользователя и проверить `approved`.
3. Найти событие и проверить `event.organizer_id == organizer_profile.id`. Это ID профиля организатора, **не** JWT `sub`/user ID.
4. Для отдельного заказа искать одновременно по `order.id` и `order.event_id == event_id`. Чужой или не относящийся к событию заказ не возвращать.

Назначение сотрудником, покупка билета и platform-admin сами по себе не дают этих прав. Владелец может одновременно быть покупателем; это не расширяет доступ к другим событиям.

| Случай | Предлагаемый ответ новых GET |
| --- | --- |
| Нет/недействителен токен | `401`, существующий формат `{"detail":"Not authenticated"}` |
| Нет профиля организатора | `404 OrganizerNotFoundError` |
| Организатор не approved | `403 OrganizerNotApprovedError` |
| Событие отсутствует | `404 EventNotFoundError` после проверки организатора |
| Событие другого организатора | `403 EventAccessDeniedError` |
| Заказ отсутствует или принадлежит другому событию | Одинаковый `404 OrderNotFoundError` после проверки доступа к выбранному событию |
| Некорректные path/query-параметры | `422 VALIDATION_ERROR` |

Пример ошибки принадлежности заказа, без сведений о его настоящем событии:

```json
{
  "error": "OrderNotFoundError",
  "message": "Order not found for this event",
  "fields": null
}
```

GET возвращает любой документированный статус заказа, а не `409` для неудобного статуса. Допустимость операции окончательно решает существующий POST refund: `409 OrderNotRefundableError` для неподходящего/уже возвращённого заказа, `402 PaymentFailedError` при отказе тестового платежа. Существующие правила доступа POST не меняются: его проверки по order ID могут отличаться от новых context GET; клиент обрабатывает и 403, и 404.

### Совместимость с refund и неизвестный результат

Клиент получает кандидата из нового списка или по `order_id` участника через новый отдельный GET. Проверяет `event_id`, показывает серверную сумму и подтверждение полного тестового возврата. Предварительный критерий кнопки — `status == confirmed`, `total_amount > 0`, `paid_at != null`; при гонке сервер всё равно может отказать. Отправляется прежний `POST /orders/7200/refund` с `{"reason":"Полный тестовый возврат"}`. URL, тело, `200 Order` и бизнес-коды существующей операции сохраняются; частичный возврат не предлагается.

После 200 клиент использует серверный ответ и обновляет новый список, участников и продажи. После `OrderNotRefundableError` перечитывает заказ, не подставляет локальный статус. При таймауте/обрыве блокирует повторную изменяющую операцию и предлагает «Проверить статус» через **новый отдельный GET в том же event-контексте**, с отключённым промежуточным кэшированием. Backend должен читать актуальное committed-состояние, без запаздывающей read replica, и атомарно обновлять статус, `refunded_at`, билеты и финансовый результат.

- `refunded` и непустой `refunded_at` подтверждают возврат.
- `confirmed` показывает лишь текущее состояние: это **не доказательство**, что исходный POST не выполняется или не поступит позже. Один GET не обеспечивает exactly-once; клиент не делает автоматический повтор POST.
- Ошибка GET не снимает блокировку неизвестного результата. Покупательские GET не используются как обход прав.

**Отдельное предложение для согласования безопасной ручной повторной попытки:** необязательный `Idempotency-Key` у существующего POST refund. При его использовании backend привязывает ключ к пользователю, заказу и телу, сериализует конкурентные операции, не выполняет второй финансовый возврат и возвращает сохранённый результат при повторе того же ключа. Несовпадение тела — новый согласуемый `409 IdempotencyConflictError`; выполняющаяся операция — новый согласуемый `409 RefundInProgressError`. Старые клиенты без заголовка сохраняют прежний контракт. Срок хранения ключей требуется явно определить. Это расширение **не существует в текущем документированном API**. До его согласования чтение позволяет подтвердить завершённый возврат, но не гарантирует безопасный повтор при неизменившемся `confirmed`.

### Критерии приёмки

Backend:

- Владелец получает только заказы своего события во всех статусах; страницы имеют стабильный порядок, корректный курсор и пустой ответ.
- Pending-профиль, сотрудник без владения, чужой организатор и заказ другого события проходят негативные проверки; порядок ошибок документирован.
- Полный refund оплаченного confirmed-заказа сохраняет исходный `total_amount`, выставляет `refunded_at`; новый GET, список, участники, продажи и покупательские чтения согласованы.
- Проверены конкурентные возвраты и потеря ответа после обработки; повтор не приводит к двум финансовым возвратам. Семантика idempotency, если принята, описана и протестирована.

Мобильный клиент после появления согласованного API:

- Читает `Page<OrganizerOrder>`, открывает заказ по серверному ID, подтверждает сумму и не предлагает возврат бесплатного/неподходящего заказа.
- Обрабатывает отказ сервера после устаревшего локального выбора, неизвестный результат и повторное чтение без автоматического POST.
- Использует общий refresh только после явного 401; очищает данные при смене сессии, игнорирует старые ответы. Обновляет участников и продажи после результата.

## 2. Полный список типов билетов организатора

### Существующий контракт и мобильный сценарий

Существующий `GET /events/{event_id}/ticket-types` публичен, возвращает `TicketType[]` только опубликованного события и исключает скрытые типы даже для владельца. Более поздний `auth-and-roles.md` уточняет: visibility этим endpoint не проверяется. Это известное ограничение приватности, а не основание расширять публичный ответ скрытыми типами. Для draft/cancelled он не является полным организаторским чтением.

Дополняются существующие операции:

- `POST /events/{event_id}/ticket-type` → `201 TicketType` (единственное число в конце).
- `PATCH /ticket-types/{ticket_type_id}` → `200 TicketType`.
- `PATCH /ticket_types/{ticket_type_id}/hide` и `/unhide` → **`200 TicketType`** по текущей Reference; underscore в этих путях сохраняется.
- `GET /events/me` → собственные события всех статусов/visibility, но без полного списка типов.

Мобильный клиент уже создаёт, редактирует, скрывает и восстанавливает типы. Он объединяет публичные результаты и успешные ответы текущей сессии по ID. После нового запуска нельзя восстановить полный список черновика/скрытых типов; отсутствие в публичном списке не подтверждает скрытие. Полное копирование типов мероприятия также ждёт этого чтения.

### Новые, ещё не согласованные endpoints

| Предлагаемый запрос | Успех | Назначение |
| --- | --- | --- |
| `GET /organizer/events/{event_id}/ticket-types` | `200 Page<TicketType>` | Все типы выбранного собственного события, включая скрытые |
| `GET /organizer/events/{event_id}/ticket-types/{ticket_type_id}` | `200 TicketType` | Один тип независимо от `is_hidden` и статуса события |

Оба чтения работают для `draft`, `published`, `cancelled`, с любой visibility. По умолчанию список всегда включает видимые и скрытые типы; `include_hidden=true` не требуется. Скрытие не означает удаление. Пустой список → `200 {"items":[],"next_cursor":null}`.

Path-параметры — положительные int. Пагинация: `limit=50` по умолчанию, диапазон 1–100, необязательный непрозрачный `cursor`, фиксированный порядок `id ASC`. Курсор привязан к `event_id` и последнему ID. Полный список означает чтение всех страниц; ответ одной страницы нельзя считать полным. После мутации клиент обновляет элемент по ID и при необходимости начинает список заново. Новая оболочка `Page<TicketType>` не меняет существующий публичный массив.

**Элемент ответа — существующий `TicketType`, без переименования и сокращения полей:** `id`, `event_id`, `name`, nullable `description`, целочисленные `price`, `quantity`, `max_per_order`, `sold_count`, `sales_start`, `sales_end`, boolean `is_hidden`. Цена `0` означает бесплатный билет. Время сохраняет момент с учётом смещения. В мобильном проекте цены типа — `Int`, итог `price × quantity` рассчитывается через `Long`; числовые пределы backend нужно согласовать с этой моделью. Чтение не создаёт новых ограничений для PATCH.

### Доступ и ошибки

Порядок новых context GET: токен → organizer profile `approved` → событие → владелец → тип с одновременным условием `ticket_type.event_id == event_id`. Правила владения и коды отсутствующего профиля/события/отказа те же, что в разделе 1. Сотрудник и покупатель без владения доступа не получают. Более ранний порядок проверок существующих PATCH по глобальному ID типа не меняется.

- Несуществующий тип или тип другого события при доступном выбранном событии → одинаковый `404 TicketTypeNotFoundError`.
- Чужое выбранное событие → `403 EventAccessDeniedError` после organizer-проверок.
- Невалидный ID, `limit` или курсор → `422 VALIDATION_ERROR`.
- Draft/cancelled или `is_hidden=true` сами по себе не являются ошибкой чтения. Доступность редактирования и изменения статуса остаётся решением существующих mutation endpoints.

Примеры ошибок:

```json
{
  "error": "TicketTypeNotFoundError",
  "message": "Ticket type not found for this event",
  "fields": null
}
```

```json
{
  "error": "EventAccessDeniedError",
  "message": "Not the event owner",
  "fields": null
}
```

```json
{
  "error": "VALIDATION_ERROR",
  "message": "Invalid pagination parameters",
  "fields": {"limit": "Must be between 1 and 100"}
}
```

### Проверка результатов изменения

| Операция | Предлагаемое поведение клиента с новыми чтениями |
| --- | --- |
| Создание с `201 TicketType` | Сохранить серверный `id`, проверить `event_id`, перечитать по новому отдельному GET; показать элемент в полном списке даже у draft |
| PATCH с `200 TicketType` | Заменить элемент по ID; при проверке перечитать его и сопоставить серверные значения с формой, включая `description: null` и моменты времени |
| Hide/unhide с `200 TicketType` | Применить серверный `is_hidden`, перечитать тот же тип; скрытый элемент остаётся в полном списке после нового запуска |
| Потеря ответа PATCH/hide/unhide | Заблокировать повтор операции до успешного отдельного GET; показать фактическое состояние, не считать отсутствие в публичном массиве доказательством скрытия |
| Потеря ответа создания, ID неизвестен | Обновить все страницы полного списка. Новые ID и совпадение полей — только кандидаты для ручной сверки, не доказательство, что создан именно этот тип |

Создание с потерянным ответом остаётся отдельным случаем: названия и настройки не уникальны, другие операции могут выполняться параллельно. **Предложение для согласования:** необязательный `Idempotency-Key` у существующего POST создания типа, со scope пользователь + событие + тело, сохранённым `201 TicketType` и защитой от двойного создания. Без такого расширения нельзя гарантировать автоматическое сопоставление результата и безопасный повтор POST; мобильный клиент не должен угадывать ID или автоматически создавать тип снова.

Новые GET должны возвращать актуальное committed-состояние. Они подтверждают состояние, а не авторство последней правки: при параллельном редактировании нужно показать различия перед ручной отправкой. Изменение цены, остатка или скрытия требует обновить посетительские типы через прежний публичный GET и пересчитать выбор; типы организаторского списка не подставляются в каталог посетителя.

### Критерии приёмки

Backend:

- Для каждого статуса события и каждой visibility владелец получает все страницы видимых и скрытых типов; отдельное чтение совпадает с элементом списка.
- Проверены чужое событие, тип другого события, отсутствие типа, pending-профиль и сотрудник без владения.
- Цепочка create → PATCH с nullable-описанием → hide → чтение скрытого → unhide сохраняет один ID и актуальные данные. Публичный список по-прежнему исключает скрытое и не раскрывает draft/cancelled.
- Потеря ответа после сохранения проверяется новым GET; согласована защита от повторного создания при неизвестном ID. OpenAPI фиксирует схемы, пагинацию и ошибки.

Мобильный клиент после появления согласованного API:

- Читает `Page<TicketType>`, догружает страницы и объединяет элементы по ID; полный ответ становится источником истины вместо списка «добавлены в этой сессии».
- После повторного запуска видит скрытый тип и может его восстановить; draft больше не зависит от публичного чтения.
- Проверяет `event_id`, сохраняет форму при ошибке, сверяет неизвестный результат, не повторяет mutation после транспортного сбоя автоматически.
- При смене сессии очищает список/форму и игнорирует старые ответы; после изменения обновляет посетительскую страницу и пересчитывает выбранные количества.

**Другие ожидаемые контракты (вне этого предложения):** поддержка — обращения, сообщения, ответы организатора и статусы; промокоды — кампании, применение скидки, Campaign QR и отчётность; PDF-билеты — защищённое скачивание и формат ответа; журнал действий — события аудита, права и пагинация. В изученных источниках согласованных контрактов для этих функций не найдено; пути и схемы здесь не выдумываются.
